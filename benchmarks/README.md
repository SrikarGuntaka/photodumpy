# Benchmarks

Every number in this directory was measured. Nothing is extrapolated, and each
report records the machine, the commit and the corpus it came from.

| File | What it measures | How it was produced |
|------|------------------|---------------------|
| [pipeline.md](pipeline.md) | End-to-end throughput as the worker fleet scales from 1 to 16 | `go run ./cmd/bench pipeline -workers 1,2,4,8,16` |
| [crash-recovery.md](crash-recovery.md) | What happens to in-flight work when a worker is SIGKILLed | `go run ./cmd/bench crash` |
| [micro.txt](micro.txt) | Raw `go test -bench` output for each algorithm, 5 runs each | see [Reproducing](#reproducing) |

## The machine

All three were run on one laptop, and its characteristics matter for reading them:

- **Intel Core Ultra 7 155H**: 16 physical cores / 22 threads, but a *hybrid*
  design — only 6 are performance cores (12 threads); the other 10 are
  efficiency and low-power cores that are substantially slower.
- **Docker Desktop on Windows**, with 22 CPUs and 7.4 GiB of memory available to
  containers. The photo directory is a Windows bind mount into the Linux VM.
- 15.4 GiB of RAM in total.

A desktop or a Linux server with uniform cores would produce different numbers,
and probably a different shape past 4 workers.

## The corpus

Synthetic, generated by `internal/fixtures` with seed 1: 68 images at
4032×3024 (12 megapixels, a phone photo's resolution), 64 MiB on disk.

Two consequences, stated plainly:

1. **Pixel count matches real photos; file size does not.** Generated scenes
   compress far better than photographs — about 1 MB per image here, against
   3–5 MB for a real 12MP JPEG. Stages whose cost scales with pixels (decoding,
   perceptual hashing, quality analysis, thumbnails) are representative. Stages
   whose cost scales with bytes (SHA-256, disk reads) are flattered.
2. **Correctness is checked, not assumed.** The generator records ground truth,
   and every timed pipeline run is verified against it — photo count, exact and
   near-duplicate groups, zero dead jobs, every photo through every stage —
   before its time is allowed to count. All 15 timed runs verified.

This project has not been benchmarked or validated against a real photo library.

## Headline results

### Scaling the worker fleet

Each worker runs 2 jobs at once; one unrecorded warm-up after each rescale, then
the median of 3 timed runs. 343 jobs per run.

| Workers | Job slots | Wall time (median) | Range | Speedup |
|---:|---:|---:|---|---:|
| 1 | 2 | 71.2 s | 70.6–72.4 s | 1.00× |
| 2 | 4 | 34.4 s | 34.1–35.4 s | 2.07× |
| 4 | 8 | 17.8 s | 17.6–17.9 s | **4.00×** |
| 8 | 16 | 15.3 s | 14.1–17.2 s | 4.66× |
| 16 | 32 | 14.4 s | 13.7–15.1 s | 4.94× |

Near-linear to 4 workers, then a plateau.

### Crash recovery

3 workers × 4 jobs each; the worker holding the most leases was SIGKILLed once
25% of jobs had succeeded.

| | |
|---|---|
| Executions interrupted by the kill | 4 |
| Re-run and completed by another worker | 4 |
| Lost | 0 |
| Dead jobs at the end | 0 of 343 |
| Kill to reclaim | 70.2 s (predicted window: 57–80 s) |
| Results after the crash | match ground truth exactly |

## What the numbers mean

The measurements above are facts about this machine. What follows is
interpretation of them, and is labelled as such.

**The plateau past 4 workers is contention inside the jobs, not in the queue.**
This is measured, not inferred: per-job latency, read from the queue's own
execution records, roughly tripled between 1 and 16 workers — thumbnail
generation's median went from 693 ms to 2,064 ms, quality analysis from 741 ms
to 1,946 ms. If the bottleneck were claiming or coordination, jobs would take
the same time once running and wait longer to start. Instead the work itself
slowed down.

*Interpretation:* 8 job slots fit on the 6 performance cores' 12 threads; 16 and
32 do not, and spill onto much slower efficiency cores. Memory bandwidth, and
the bind-mounted photo directory, are plausible additional contributors that
these measurements cannot separate.

**The queue itself is not the limit.** `SELECT … FOR UPDATE SKIP LOCKED` means
workers skip each other's claimed rows rather than blocking on them; the
near-linear 1→4 scaling is the evidence that claims are not serialising work.

**Metadata extraction never touches pixels.** Reading a 12MP photo's metadata
costs 30 µs, against 188 ms to decode the same file for its perceptual hash —
because dimensions come from the JPEG header and dates and GPS from the EXIF
segment.

**The quadratic similarity scan is cheap at library scale.** 10,000 photos is 50
million pair comparisons, measured at 57–82 ms. The bucketing optimisation
described in DESIGN_DECISIONS.md stays unbuilt, because nothing has shown this to
be a bottleneck.

**The micro-benchmarks are noisy, and the noise has a shape.** Ranges run from a
few percent to nearly 2× between runs. In a separate run of
`GroupSimilar/n=10000`, results fell into two clusters near 40 ms and 70 ms with
nothing between. *Interpretation:* that bimodal pattern is what one would expect
if the Windows scheduler placed a single-threaded benchmark on a performance core
in some runs and an efficiency core in others. It is also why no benchmark here
is subtracted from another — on this machine, the difference between two noisy
medians is not a measurement.

## Reproducing

The stack must be running (`docker compose up -d`). The tool generates the
corpus under `sample-photos/_bench` on first use and reuses it after.

```bash
go run ./cmd/bench pipeline -workers 1,2,4,8,16
go run ./cmd/bench crash
go test -run '^$' -bench . -benchmem -count 5 ./internal/clustering ./internal/duplicates ./internal/hashing ./internal/metadata ./internal/quality ./internal/thumbnail
go run ./cmd/bench clean    # remove the benchmark corpus afterwards
```

The pipeline sweep takes about 13 minutes on the machine above. Keep the
machine awake and otherwise idle: one earlier crash-demo run was invalidated when
the laptop slept mid-run, and the tool produced no report rather than a wrong
one.

`cmd/bench` refuses to count a run it cannot trust. A run whose results do not
match ground truth is reported as failed, and a run during which a worker
container stopped, restarted or was OOM-killed is reported as invalid — lease
recovery would make such a run verify while its wall time measured a 60-second
lease expiry instead of throughput.
